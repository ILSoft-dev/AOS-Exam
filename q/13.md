<div class="tldr" markdown="1">
**Критическая секция (КС)** — часть программы, в которой поток обращается к **разделяемым данным**. Результат зависит от того, не изменил ли данные другой поток в это же время. Чтобы исключить гонки, нужно обеспечить **взаимное исключение**: в критической секции по одному и тому же ресурсу в каждый момент может находиться **только один поток**.

Требования к решению (условия Дейкстры):
1. **Взаимное исключение.**
2. **Прогресс:** поток вне КС не мешает другим войти в неё.
3. **Ограниченное ожидание:** нет бесконечного откладывания (голодания).
4. **Нет предположений о скоростях** потоков и числе процессоров.

Способы реализации: **запрет прерываний**, **блокирующие переменные** (с TSL), **алгоритмы Деккера и Петерсона**, **семафоры и мьютексы**, объект **CRITICAL_SECTION** в Windows.
</div>

## Структура программы с критической секцией

```text
while (true) {
    вход в КС          ← протокол входа (захват)
    критическая секция ← работа с общими данными
    выход из КС        ← протокол выхода (освобождение)
    остальной код
}
```

Критическая секция всегда связана с **конкретным ресурсом**. Потоки, работающие с разными ресурсами, друг другу не мешают. КС нужно делать **как можно короче**, чтобы другие потоки меньше ждали.

## Способы реализации

### 1. Запрет прерываний

Поток запрещает прерывания на время КС. Тогда ОС не может переключить процессор на другой поток.
- ➕ Просто.
- ➖ Опасно давать такую возможность пользовательским программам: можно «повесить» систему.
- ➖ **Не работает на многопроцессорных системах**: запрет действует только на одно ядро.
- Используется **только внутри ядра** для коротких участков.

### 2. Программные решения

**Наивная блокирующая переменная** (флаг) **не работает**, потому что проверка и установка флага не атомарны. Два потока могут одновременно увидеть «свободно» ([вопрос 14]({{ '/q/14.html' | relative_url }})).

**Строгое чередование** (переменная `turn`) гарантирует взаимное исключение, но нарушает **прогресс**: потоки обязаны входить строго по очереди.

**Алгоритм Петерсона** (1981) — корректное программное решение для двух потоков:

```c
int  turn;          // чья очередь уступать
bool want[2];       // желание войти

void enter(int i) {          // i = 0 или 1
    int j = 1 - i;
    want[i] = true;          // хочу войти
    turn = j;                // но уступаю другому
    while (want[j] && turn == j)
        ;                    // активное ожидание
}
void leave(int i) { want[i] = false; }
```

Если оба хотят войти одновременно, войдёт тот, кто записал `turn` **первым**: второй поток своей записью уступил ему очередь и будет ждать. Похожее, более раннее решение — **алгоритм Деккера**.
- ➖ Активное ожидание тратит процессор. На современных процессорах нужны барьеры памяти.

### 3. Аппаратная поддержка: атомарные команды

Процессоры имеют неделимые команды: **TSL (Test and Set Lock)**, **XCHG**, **CAS (Compare and Swap)**. Они позволяют корректно реализовать блокирующие переменные и спин-блокировки ([вопрос 14]({{ '/q/14.html' | relative_url }})).

### 4. Средства ОС: ожидание без затрат процессора

Чтобы ждущий поток **не крутился в цикле**, ОС переводит его в **состояние ожидания** и будит, когда ресурс освободится. Так работают **семафоры, мьютексы, мониторы** ([вопрос 15]({{ '/q/15.html' | relative_url }})).

## Критические секции в Windows

В WinAPI есть объект **`CRITICAL_SECTION`** для синхронизации потоков **одного процесса**:

```c
CRITICAL_SECTION cs;
InitializeCriticalSection(&cs);

// в каждом потоке:
EnterCriticalSection(&cs);   // вход (захват)
count++;                     // работа с общими данными
LeaveCriticalSection(&cs);   // выход

DeleteCriticalSection(&cs);
```

- Работает **быстрее мьютекса**: если КС свободна, вход выполняется атомарной операцией **без перехода в ядро**. Только при конфликте поток переходит в ожидание на объекте ядра. Можно задать короткое **вращение (spin count)** перед засыпанием.
- Ограничение: только **внутри одного процесса**. Для синхронизации разных процессов нужен **мьютекс**.

### C#

```csharp
private static readonly object locker = new object();
private static int count;

void Worker() {
    for (int i = 0; i < 1_000_000; i++)
        lock (locker) {      // Monitor.Enter / Monitor.Exit
            count++;
        }
}
```

Для простых счётчиков быстрее `Interlocked.Increment(ref count)`.
