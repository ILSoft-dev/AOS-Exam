<div class="tldr" markdown="1">
**Виртуализация памяти** — механизмы, которыми гипервизор даёт каждой ВМ **иллюзию собственной непрерывной физической памяти**, хотя на самом деле она выделяется из общей памяти хоста.

В ВМ появляется **три вида адресов**:
- **GVA** (гостевой виртуальный) → гостевая ОС по своим таблицам страниц →
- **GPA** (гостевой физический) → гипервизор →
- **HPA** (физический адрес хоста).

Способы реализации двухуровневой трансляции:
- **теневые таблицы страниц (shadow page tables)** — гипервизор строит таблицы GVA → HPA и синхронизирует их с гостевыми. Программный способ, большие накладные расходы;
- **аппаратная вложенная трансляция** — **Intel EPT**, **AMD NPT (RVI)**: процессор сам проходит оба уровня таблиц.

Методы экономии памяти: **перераспределение (overcommit)**, **балунинг (ballooning)**, **дедупликация страниц** (TPS в VMware, **KSM** в Linux), **сжатие** и **свопинг** на уровне гипервизора, **динамическая память** Hyper-V.
</div>

## Проблема

Обычная ОС уверена, что управляет **реальной физической памятью** с адреса 0. В ВМ таких ОС несколько, а реальная память одна. Гипервизор должен:
- дать каждой ВМ «свою» физическую память, начинающуюся с 0;
- **изолировать** ВМ друг от друга;
- **эффективно** использовать реальную память и по возможности выделять ВМ в сумме больше, чем есть.

## Три уровня адресов

<pre class="diagram">
Приложение в ВМ
   GVA  (гостевой виртуальный)
    │  таблицы страниц ГОСТЕВОЙ ОС
    ▼
   GPA  (гостевой «физический»)
    │  таблицы ГИПЕРВИЗОРА
    ▼
   HPA  (реальный физический хоста)
</pre>

Аппаратная MMU без поддержки виртуализации умеет делать только **одно** преобразование. Как реализовать два?

## Способ 1: теневые таблицы страниц (shadow page tables)

- Для каждого процесса гостя гипервизор строит **теневую таблицу** со сквозным отображением **GVA → HPA**. Именно её загружает в MMU реального процессора.
- Гостевые таблицы страниц **защищаются от записи**. Когда гостевая ОС меняет свою таблицу, происходит перехват, и гипервизор **обновляет теневую** таблицу.
- Переключение процессов в госте (запись в CR3) тоже перехватывается.
- ➕ Работает на любых процессорах, обращение к памяти так же быстро, как без виртуализации.
- ➖ **Большие накладные расходы**: частые перехваты при изменении таблиц и переключении процессов, дополнительная память под теневые таблицы, сложность реализации.

## Способ 2: аппаратная вложенная трансляция (SLAT)

**SLAT (Second Level Address Translation)**: **Intel EPT (Extended Page Tables)**, **AMD NPT (Nested Page Tables) / RVI**.

- Процессор имеет **два указателя на таблицы**: гостевые таблицы (GVA → GPA), которыми гость управляет **сам, без перехватов**, и таблицы гипервизора (GPA → HPA).
- MMU **аппаратно проходит оба уровня**.
- ➕ Не нужны перехваты при изменении гостевых таблиц, гипервизор проще.
- ➖ **Промах TLB дороже**: при 4-уровневых таблицах на каждом уровне гостевой таблицы нужен проход по таблице хоста, до **24 обращений к памяти** вместо 4. Смягчается TLB с тегами ВМ (**VPID/ASID**: не нужно сбрасывать TLB при переключении ВМ) и **большими страницами**.
- Сегодня SLAT — стандарт. Например, Hyper-V в клиентских Windows **требует** SLAT.

## Методы экономии и перераспределения памяти

### Перераспределение (memory overcommit)

ВМ в **сумме** выделено больше памяти, чем физически есть на хосте. Это работает, потому что ВМ редко используют всю выделенную память одновременно. Для этого нужны механизмы ниже.

### Балунинг (memory ballooning)

<pre class="diagram">
Гостевая ОС
┌─────────────────────────┐
│ приложения │ ◯ «шар»    │
│            │ (драйвер   │
│            │ занимает   │
│            │ память)    │
└─────────────────────────┘
   надуть → гость отдаёт страницы
   гипервизору для других ВМ
</pre>

- В гостевой ОС работает **драйвер-«шар» (balloon driver)**, который является паравиртуальным элементом.
- Когда хосту нужна память, гипервизор просит драйвер **«надуться»**: драйвер запрашивает память у гостевой ОС как обычное приложение. Гостевая ОС сама решает, что освободить: сначала кеш, потом выгрузка в свой файл подкачки. Страницы, которые занял «шар», гипервизор **отдаёт другим ВМ**.
- **«Сдутие»** возвращает память гостю.
- ➕ Гость сам выбирает, какие страницы освободить, и делает это разумнее гипервизора.
- Есть в VMware (vmmemctl), Hyper-V, KVM (virtio-balloon), Xen.

### Дедупликация (совместное использование) одинаковых страниц

- Многие ВМ запущены с **одинаковыми ОС**, поэтому в памяти много **идентичных страниц**: код ядра, библиотеки, нулевые страницы.
- Гипервизор **находит** одинаковые страницы (по хешу содержимого), оставляет **одну копию** и отображает её во все ВМ **только для чтения**.
- При попытке записи срабатывает **копирование при записи (copy-on-write)**: ВМ получает свою копию.
- Реализации: **TPS (Transparent Page Sharing)** в VMware, **KSM (Kernel Same-page Merging)** в Linux/KVM.
- ⚠️ Риск **атак по сторонним каналам** между ВМ, поэтому межмашинная дедупликация в VMware сейчас по умолчанию отключена.

### Сжатие памяти и свопинг гипервизора

- **Сжатие** — редко используемые страницы сжимаются в памяти: это быстрее, чем выгрузка на диск.
- **Свопинг на уровне гипервизора** — крайняя мера: гипервизор выгружает страницы ВМ на диск **без ведома гостя**. Это может давать сильное замедление («двойная подкачка»).

### Динамическая память (Hyper-V)

Для ВМ задаются **начальный, минимальный и максимальный** объём и **буфер**. Hyper-V **автоматически добавляет** память (горячее добавление) или **забирает** её (через балунинг) в зависимости от нагрузки.

## Сравнение способов трансляции

| | Теневые таблицы | Аппаратная (EPT/NPT) |
|---|---|---|
| Реализация | Программно, гипервизор | Аппаратно, MMU процессора |
| Перехваты при изменении гостевых таблиц | Много | Нет |
| Стоимость промаха TLB | Как без виртуализации | Выше (двумерный обход таблиц) |
| Память под таблицы | Теневые таблицы на каждый процесс гостя | Одна таблица GPA → HPA на ВМ |
| Требования | Любой процессор | Intel EPT (с Nehalem) / AMD NPT |
