<div class="tldr" markdown="1">
**Сегментно-страничное распределение** объединяет оба метода. Адресное пространство процесса делится на **сегменты** (логические части), а каждый сегмент — на **страницы** фиксированного размера. Физическая память делится на **кадры**.

Виртуальный адрес = **(номер сегмента, номер страницы в сегменте, смещение)**. Преобразование **двухэтапное**: по **таблице сегментов** находится **таблица страниц** этого сегмента, а по ней — **номер кадра**. Физический адрес = кадр ‖ смещение.

➕ Сочетает **логичность, защиту и разделение** сегментов с **отсутствием внешней фрагментации** и эффективной подкачкой страниц. ➖ Сложность, **больше обращений к таблицам** (нужен TLB), внутренняя фрагментация в последней странице каждого сегмента.

Пример: процессоры **Intel x86** в защищённом режиме (сегментация + страничное преобразование), системы MULTICS.
</div>

## Почему объединяют

| Метод | Сильная сторона | Слабая сторона |
|---|---|---|
| Сегменты | Логическая структура, защита, разделение | Внешняя фрагментация, перемещение больших сегментов |
| Страницы | Нет внешней фрагментации, эффективная подкачка | Не отражают логику программы |
| **Сегменты + страницы** | **Всё лучшее** от обоих | Сложность и накладные расходы |

## Структура

- Каждый процесс имеет **таблицу сегментов**.
- Дескриптор сегмента содержит не физическую базу, а **адрес таблицы страниц этого сегмента**, а также **длину сегмента** (в страницах) и **права доступа**.
- Каждый сегмент имеет **свою таблицу страниц**.
- В ОЗУ находятся только нужные **страницы** нужных сегментов. Сегмент не обязан лежать в памяти целиком и непрерывно.

## Преобразование адреса

<pre class="diagram">
Виртуальный адрес
┌──────┬──────────┬──────────┐
│ сег s│ стр. p   │ смещ. d  │
└──┬───┴────┬─────┴────┬─────┘
   │        │          │
   ▼        │          │
Таблица сегментов[s]   │
 → адрес табл. страниц │
   и длина сегмента    │
   │  (p < длины?)     │
   ▼        ▼          │
Таблица страниц сег. s[p]
 → номер кадра f       │
   │                   │
   ▼                   ▼
┌──────────────┬──────────┐
│   кадр f     │  смещ. d │  физический адрес
└──────────────┴──────────┘
</pre>

1. По номеру сегмента **s** найти дескриптор в таблице сегментов. Проверить права и то, что **p** не выходит за длину сегмента.
2. Из дескриптора взять адрес **таблицы страниц** сегмента.
3. По номеру страницы **p** найти номер **кадра f**. Если страница отсутствует, возникает **страничное прерывание**.
4. Физический адрес = **f × размер страницы + d**.

**Пример.** Размер страницы 1 КБ (1024 Б). Адрес (s = 1, p = 2, d = 100). В таблице сегментов сегмент 1 содержит 5 страниц, права «чтение-запись». В его таблице страниц страница 2 → кадр 7.
Физический адрес = 7 × 1024 + 100 = **7268**.

### Вариант Intel x86 (защищённый режим, 32 бита)

<pre class="diagram">
логический адрес (селектор : смещение)
      │  сегментация (GDT/LDT)
      ▼
линейный адрес (32 бита)
      │  страничное преобразование
      │  (каталог → таблица → кадр)
      ▼
физический адрес
</pre>

Здесь сегментация сначала даёт **линейный (виртуальный) адрес**: база сегмента + смещение. Затем линейный адрес преобразуется **страничным механизмом**. Windows и Linux настраивают все сегменты на базу 0 («плоская модель»), поэтому фактически работает только страничное преобразование.

## Затраты и их снижение

- Каждое обращение к памяти требует **двух дополнительных обращений** (к таблице сегментов и таблице страниц), а с многоуровневыми таблицами ещё больше.
- **TLB** (ассоциативная память) кеширует готовые преобразования и почти полностью снимает эту проблему.

## Достоинства и недостатки

- ➕ Логическая организация программы, **защита** и **разделение** на уровне сегментов.
- ➕ **Нет внешней фрагментации**, не нужно сжатие.
- ➕ Эффективная **подкачка по страницам**: сегмент может быть больше ОЗУ и загружаться частично.
- ➖ **Сложность** аппаратуры и ОС.
- ➖ Объём таблиц: таблица страниц на каждый сегмент.
- ➖ **Внутренняя фрагментация** в последней странице каждого сегмента.
- ➖ Замедление преобразования без TLB.
