<div class="tldr" markdown="1">
**Блокирующая переменная** — двоичная переменная, связанная с разделяемым ресурсом. Её значение показывает, **свободен ли ресурс** (например, 1 — свободен, 0 — занят). Поток перед входом в критическую секцию **проверяет** переменную. Если ресурс свободен, поток **устанавливает** «занято» и входит. Если занят, поток ждёт. При выходе поток сбрасывает переменную в «свободно».

Проблема: операция **«проверить и установить» должна быть неделимой**. Иначе оба потока увидят «свободно» и войдут одновременно. Решение — специальная **атомарная команда процессора TSL (Test-and-Set Lock)** / XCHG / CAS.

Недостаток — **активное ожидание (busy waiting)**: ждущий поток крутится в цикле и тратит процессорное время. Улучшение — функции ОС **WAIT(D)/POST(D)**, которые переводят поток в состояние ожидания. Блокирующие переменные с активным ожиданием называют **спин-блокировками (spinlock)**. Они полезны в ядре на многопроцессорных системах для очень коротких секций.
</div>

## Идея

Каждому разделяемому ресурсу ставится в соответствие **переменная F(D)**:
- `F(D) = 1` — ресурс **свободен**;
- `F(D) = 0` — ресурс **занят**.

<pre class="diagram">
       ┌──────────────┐
  ┌──► │ F(D) = 1 ?   │── нет (занят) ─┐
  │    └──────────────┘                │
  │           │ да                     │
  │           ▼                        │
  │    F(D) := 0  (занять)             │
  │           ▼                        │
  │    Критическая секция              │
  │           ▼                        │
  │    F(D) := 1  (освободить)         │
  │                                    │
  └──────────── повторить проверку ◄───┘
</pre>

## Почему наивная реализация не работает

```c
int lock = 0;              // 0 — свободно, 1 — занято

void enter(void) {
    while (lock == 1) ;    // (1) проверка
    lock = 1;              // (2) установка
}
void leave(void) { lock = 0; }
```

Между шагами **(1)** и **(2)** поток может быть прерван:

| Поток A | Поток B |
|---|---|
| видит `lock == 0` | |
| ← переключение | видит `lock == 0` |
| | `lock = 1`, входит в КС |
| `lock = 1`, **тоже входит в КС** ❌ | |

Взаимное исключение нарушено. Значит, **проверка и установка должны выполняться одной неделимой операцией**.

## Решение: команда TSL (Test and Set Lock)

**TSL** — команда процессора, которая **атомарно** читает значение ячейки памяти и записывает в неё 1. На время её выполнения шина памяти блокируется для других процессоров.

```nasm
enter_region:
    TSL  REG, LOCK      ; REG := LOCK; LOCK := 1  (атомарно)
    CMP  REG, #0        ; было ли свободно?
    JNE  enter_region   ; нет — повторить (крутимся)
    RET                 ; да — вошли в КС

leave_region:
    MOV  LOCK, #0       ; освободить
    RET
```

В x86 аналог — **`XCHG`** (обмен регистра с памятью) или `LOCK BTS`, а также **CMPXCHG** (compare-and-swap). В C/C++ используются `__sync_lock_test_and_set` и `std::atomic_flag::test_and_set`, в Windows — `InterlockedExchange`.

```c
#include <stdatomic.h>
atomic_flag lock = ATOMIC_FLAG_INIT;

void enter(void) { while (atomic_flag_test_and_set(&lock)) ; }
void leave(void) { atomic_flag_clear(&lock); }
```

## Недостаток: активное ожидание

Пока ресурс занят, ждущий поток **непрерывно выполняет цикл проверки** и тратит процессорное время. На однопроцессорной машине это особенно плохо: поток, держащий блокировку, не может работать, пока ждущий крутится до конца своего кванта.

Возможна и **инверсия приоритетов**: высокоприоритетный поток крутится и не даёт выполниться низкоприоритетному, который держит блокировку.

### Решение: системные функции WAIT и POST

ОС вводит функции, которые **не крутятся, а блокируют поток**:
- **WAIT(D)** — если ресурс D занят, поток переводится в **состояние ожидания**. В его дескрипторе отмечается, что он ждёт ресурс D.
- **POST(D)** — освобождает ресурс и переводит все потоки, ждущие D, в **состояние готовности**. Планировщик выбирает один из них, и тот снова проверяет переменную.

<pre class="diagram">
 ┌─► F(D)=1? ── нет ─► WAIT(D): поток
 │      │да              уходит в ожидание
 │      ▼                     │
 │   F(D):=0                  │ POST(D)
 │      ▼                     │ от другого
 │   КС                       │ потока
 │      ▼                     │
 │   F(D):=1; POST(D) ────────┘
 └────────────────────────── повторить
</pre>

Так процессор не тратится на ожидание. Это прямой предшественник **семафоров** ([вопрос 15]({{ '/q/15.html' | relative_url }})).

## Спин-блокировки сегодня

Активное ожидание не всегда плохо. На **многопроцессорных** системах, если критическая секция очень короткая (десятки команд), **дешевле покрутиться**, чем усыплять и будить поток: переключение контекста стоит тысячи тактов.
- Ядра Windows и Linux широко используют **спин-блокировки** для защиты своих структур.
- Объект `CRITICAL_SECTION` в Windows сначала немного крутится (spin count), а уже потом засыпает. Это гибрид.

| | Блокирующая переменная со спином | WAIT/POST, семафор |
|---|---|---|
| Ожидание | Активное (цикл) | Пассивное (поток спит) |
| Затраты процессора при ожидании | Есть | Нет |
| Затраты на захват без конфликта | Минимальные | Выше (вызов ядра) |
| Когда выгодно | Короткие КС, многопроцессорные системы, ядро | Длинные КС, одно ядро |
