<div class="tldr" markdown="1">
**Распределённое приложение** — приложение, части которого выполняются **на разных компьютерах сети** и взаимодействуют через сеть.

Любое приложение логически состоит из **трёх уровней (слоёв)**:
1. **Представление** (интерфейс пользователя);
2. **Логика приложения** (бизнес-логика, обработка);
3. **Данные** (хранение, управление базой данных).

**Модели распределённых приложений** различаются тем, как эти уровни распределены между клиентом и сервером:
- **файловый сервер** — на клиенте всё, сервер только хранит файлы;
- **удалённый доступ к данным** — СУБД на сервере, логика на клиенте («толстый клиент»);
- **сервер баз данных** — часть логики на сервере в хранимых процедурах;
- **сервер приложений (трёхзвенная модель)** — логика вынесена на отдельный сервер, клиент «тонкий» (браузер).

Также: **одноранговая (P2P)** модель, **сервис-ориентированная (SOA)**, **микросервисы**.
</div>

## Функциональные уровни приложения

<pre class="diagram">
┌──────────────────────────────┐
│ 1. Представление (UI)        │  ввод, вывод, формы
├──────────────────────────────┤
│ 2. Логика приложения         │  расчёты, правила
├──────────────────────────────┤
│ 3. Управление данными        │  СУБД, файлы
└──────────────────────────────┘
</pre>

Иногда выделяют больше: **представление**, **интерфейс** представления, **прикладная логика**, **логика данных** (запросы), **операции с данными** (СУБД), **файловые операции** (ОС).

## Модели

### 1. Модель «файловый сервер»

<pre class="diagram">
Клиент                       Сервер
[UI + логика + СУБД] ◄─сеть─► [файлы БД]
</pre>
- На клиенте выполняется **всё**: интерфейс, логика, даже СУБД (например, файловые базы dBase, Access на сетевом диске).
- Сервер — это просто **сетевое файловое хранилище**.
- ➖ По сети передаются **целые файлы или большие блоки**: большой трафик. Слабая целостность данных при одновременной работе.
- ➕ Простота.

### 2. Модель удалённого доступа к данным (двухзвенная клиент-сервер, «толстый клиент»)

<pre class="diagram">
Клиент                      Сервер БД
[UI + логика] ──SQL-запрос─► [СУБД + данные]
              ◄──результат──
</pre>
- **СУБД** работает на сервере, а клиент посылает **SQL-запросы** и получает только **результат**.
- ➕ Трафик меньше, целостность обеспечивает СУБД.
- ➖ Логика на каждом клиенте, поэтому обновлять программу сложно. «Толстый клиент» требует ресурсов.

### 3. Модель сервера баз данных

- Часть **прикладной логики** переносится на сервер в виде **хранимых процедур** и **триггеров**.
- Клиент вызывает процедуру по имени: меньше трафика, логика централизована.
- ➖ Сервер БД перегружен, логика привязана к конкретной СУБД.

### 4. Модель сервера приложений (трёхзвенная архитектура)

<pre class="diagram">
Клиент          Сервер            Сервер
(тонкий)        приложений        БД
[UI]  ◄─HTTP─►  [логика]  ◄─SQL─► [данные]
</pre>
- **Логика** выполняется на отдельном **сервере приложений**.
- Клиент «**тонкий**»: браузер или простое приложение.
- ➕ Масштабируемость (можно добавить серверы), централизованное обновление, безопасность (клиент не имеет прямого доступа к БД).
- ➖ Сложность разработки и администрирования.
- Пример: веб-приложения (браузер → веб-сервер и ASP.NET/Java → SQL Server/PostgreSQL), 1С в клиент-серверном режиме.

**Многозвенная (N-tier)** архитектура — развитие трёхзвенной: добавляются балансировщики, кеши, очереди.

## Другие модели

### Одноранговая (peer-to-peer, P2P)

- **Нет выделенного сервера**: каждый узел и клиент, и сервер.
- ➕ Нет единой точки отказа, масштабируемость.
- ➖ Сложно управлять, обеспечивать безопасность и согласованность.
- Примеры: BitTorrent, блокчейн, рабочие группы Windows.

### Сервис-ориентированная архитектура (SOA) и микросервисы

- Приложение строится из **независимых сервисов**, которые общаются по сети (HTTP/REST, gRPC, очереди сообщений).
- **Микросервисы** — небольшие независимые сервисы, у каждого своя БД. Развёртываются в **контейнерах** (Docker, Kubernetes).
- ➕ Независимое развитие и масштабирование, отказоустойчивость.
- ➖ Сложность распределённой системы: сеть, согласованность данных, мониторинг.

### Облачные модели

**IaaS** (инфраструктура как услуга), **PaaS** (платформа), **SaaS** (программа как услуга), **serverless** (функции).

## Требования к распределённым системам

- **Прозрачность** — пользователь не видит, где находятся ресурсы: прозрачность расположения, доступа, репликации, отказов.
- **Масштабируемость**.
- **Отказоустойчивость**.
- **Открытость** — стандартные протоколы.
- **Безопасность**.

## Сравнение

| Модель | Где логика | Трафик | Клиент | Пример |
|---|---|---|---|---|
| Файловый сервер | Клиент | Очень большой | Толстый | Access на общем диске |
| Удалённый доступ к данным | Клиент | Средний | Толстый | Delphi + SQL Server |
| Сервер БД | Клиент + хранимые процедуры | Малый | Толстый | Хранимые процедуры PL/SQL |
| Сервер приложений | Сервер приложений | Малый | Тонкий | Веб-приложения |
| P2P | Все узлы | — | Узел | BitTorrent |
